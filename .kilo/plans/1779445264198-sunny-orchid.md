# 計画: CDDA Mod開発フローの9ステップ化

## 背景

現在の `rules/CORE.md` および `cdda_mod_dev_plan.md` は、設計書→実装→検証という大まかな流れを記載しているが、以下の点で粒度が粗い。

- 「設計書」が1段階しかない（ユーザーのフローでは「仕様書」と「計画書」の2段階に分かれている）
- 「批判的に分析してブラッシュアップ」という工程が明示されていない
- 「バランス調整」という工程が明示されていない

ユーザーはより厳密な9ステップの開発フローをルール化したい。

## ユーザーの9ステップ

1. jsonを含まない仕様書の作成（小規模modなら省略）
2. 仕様書を批判的に分析してブラッシュアップ
3. 計画書を作成
4. external/cdda/data/json/ の記述と比較して計画書に矛盾点がないか確認
5. 計画書を批判的に分析してブラッシュアップ
6. 計画書に基づいて実装
7. scripts/check_mods.sh を用いて読み込みエラーが出ない状態にする
8. ユーザーが期待した動作になっているか確認する（バグがないかの確認）
9. バランス調整を行う

## 実装方針

既存の `rules/CORE.md` 基本ルールと `cdda_mod_dev_plan.md` 開発計画書に、上記9ステップを統合する。

### 変更対象ファイル

1. **`templates/spec_template.md`（新規作成）**
   - ステップ1用の「仕様書（Specification）」テンプレート
   - JSONを含まない、純粋な概念設計・要件定義
   - 含むもの：目的、スコープ、背景ストーリー、ゲームプレイへの影響、含まないもの、成功基準

2. **`templates/design_template.md`（更新）**
   - ステップ3用の「計画書（Design/Plan）」テンプレート
   - 既存の内容をベースに、仕様書からの情報継承を明確化
   - 実装順序、ファイル構成、CDDA参照ファイル、テスト手順を含む
   - 「仕様書から継承」セクションを追加

3. **`rules/CORE.md`（更新）**
   - 「開発の進め方」を9ステップ形式に書き換え
   - 各ステップの目的と必須/省略条件を記載
   - 小規模modの定義（例：jsonファイル1〜2個、単純なアイテム追加のみ）を明記
   - ステップ2・5の「批判的分析」の具体的内容（AIによる自己レビュー、他者レビューの促進）を記載
   - ステップ4の「external/cdda/ 参照」との重複を整理
   - ステップ9の「バランス調整」の指針を簡潔に記載

4. **`cdda_mod_dev_plan.md`（更新）**
   - 「5. 作業フロー」の「新規mod作成」セクションを9ステップに置き換え
   - 既存の検証レベル（Level1/2/3）をステップ7〜9にマッピング
   - 旧mod移植フローには影響を与えない（別セクションのため）

### 確定事項（ユーザー回答反映）

- **仕様書と計画書の役割分担**: 仕様書=概念設計・要件定義（JSONなし）、計画書=技術設計・実装詳細。ユーザーの理解と一致。
- **批判的分析の実行者**: AIエージェント（Kilo等）に自己レビューを要求する工程として記載。プロンプト例も提供する。
- **バランス調整の指標**: 具体的な比較方法を記載。既存コンテンツとの数値比較（±20%基準等）を明示する。

## 変更詳細（確定案）

### ファイル間の情報分割ルール

| ファイル | 役割 | 記載内容 |
|---|---|---|
| `rules/CORE.md` | 全モデル必読の詳細手順 | 9ステップの各工程の手順、チェックリスト、プロンプト例、小規模modの定義 |
| `cdda_mod_dev_plan.md` | 人間向け開発計画書・全体俯瞰 | 9ステップの概要図、検証レベルの定義、旧mod移植フロー、ディレクトリ構成 |
| `templates/spec_template.md` | ステップ1の入力 | 概念設計のテンプレート構造 |
| `templates/design_template.md` | ステップ3の入力 | 技術設計のテンプレート構造 |

### 1. `templates/spec_template.md`（新規作成）

```markdown
## Mod仕様書: [mod名]

### 背景・動機
- なぜこのmodが必要か
- 解決する問題や追加する体験

### 追加/変更内容（What）
- 含むもの（具体的に）
- 含まないもの（境界を明確化）

### ゲームプレイへの影響（Why）
- プレイヤーの体験がどう変わるか
- 既存システムとの関係性

### 成功基準
- どうなればこのmodは完成と見なせるか
- テストプレイで確認すべきポイント

### スコープ判断
- 小規模mod（ステップ1省略対象）か判断する根拠
```

### 2. `templates/design_template.md`（更新）

既存の内容に以下を追加：
- **「仕様書から継承」セクション**: Step 1で決定した目的・スコープ・成功基準をそのまま転記
- **「使用予定ID一覧」セクション**: Step 4で確認する対象を明示化
- **「参照ファイル（実在確認済み）」セクション**: Step 4を実施した上でチェックマークをつける欄

### 3. `rules/CORE.md`（更新）

#### 小規模modの定義（Step 1省略条件）
以下**すべて**を満たす場合、Step 1（仕様書作成）とStep 2（仕様書レビュー）を省略可能：
- 新規JSONエントリが5個以下
- 既存タイプの `copy-from` のみ（新規 `type` 定義なし）
- 既存システムの拡張のみ（新規ゲームシステム・マップジェネレータ・NPC行動ロジック等を追加しない）
- 既存の同カテゴリアイテムから明確に派生したもの（例：「iron_rod をベースにした新素材の棍棒」）

#### 9ステップ詳細

```markdown
## 開発の進め方（9ステップ）

### Step 1: 仕様書作成（小規模modは省略可）
- `templates/spec_template.md` を使用
- このmodが何を追加/変更し、ゲームプレイにどう影響するかを記述
- JSON構文を含めない
- **省略条件**: 小規模modの定義（前述）を満たす場合

### Step 2: 仕様書レビュー
- 以下のプロンプトをAIエージェントに実行：
  ```
  以下のmod仕様書を批判的にレビューしてください。
  - この仕様は既存のCDDAゲームシステムと矛盾していないか
  - スコープが適切か（過大でないか、過小でないか）
  - プレイヤー体験として面白いか、実用的か
  - 改善案や削減すべき範囲があれば指摘してください
  ```
- レビュー結果を反映して仕様書をブラッシュアップ
- **省略条件**: Step 1を省略した場合

### Step 3: 計画書作成
- `templates/design_template.md` を使用
- Step 1の仕様書を基に、実装の詳細を記述
- 使用するtype、copy-from先、ID命名、依存関係を決定
- **使用予定ID一覧**と**参照ファイル一覧**を明記

### Step 4: CDDA参照との整合性確認
- `external/cdda/data/json/` で計画書に記載した以下を実在確認：
  - copy-from先のID
  - 使用予定のフラグ名
  - 使用予定のマテリアルID
  - レシピの `activity_level` 参照値
- design_template.md の「参照ファイル（実在確認済み）」欄にチェックをつける

### Step 5: 計画書レビュー
- 以下のプロンプトをAIエージェントに実行：
  ```
  以下のmod計画書を技術的観点から批判的にレビューしてください。
  - ID命名規則に違反がないか（prefix統一、使用可能文字）
  - copy-from先が適切か、不要なフィールドの上書きがないか
  - 依存関係に漏れがないか
  - 実装後の修正コストが高い設計がないか
  - 計画書とexternal/cdda/data/json/の実際のデータに矛盾がないか
  ```
- レビュー結果を反映して計画書をブラッシュアップ

### Step 6: 実装
- 計画書に基づき、modinfo.json および data/*.json を作成
- 編集のたびに `scripts/validate.sh` を実行（Level1）
- 実装中に計画書から逸脱する場合は、都度計画書を更新する

### Step 7: 読み込みエラー解消（Level2）
- `scripts/link_mod_for_test.sh` でCDDAに配置
- `scripts/check_mods.sh <mod_id>` でmod読み込みチェック
- エラーが出ない状態にする
- 詳細は `rules/verification.md` 参照
- **前提条件**: `external/cdda/cataclysm-tiles` が存在し、modが `external/cdda/mods/` に配置済みであること

### Step 8: 動作確認（Level3）
- CDDAを起動し、mod有効化時にエラーが出ないことを確認
- デバッグメニューでスポーン、クラフト、効果を確認
- 仕様書に記載した「成功基準」を満たしているか検証
- バグ（意図しない動作）を発見したら記録し、Step 6に戻って修正

### Step 9: バランス調整
- 追加アイテム/仕様の性能を、**同カテゴリ・同入手難易度帯**の既存コンテンツと比較：
  - 武器: ダメージ vs 重量 vs 製作難易度（技能レベル・素材の希少性）
  - 防具: 防御値 vs 環境耐性 vs 重量 vs 機動性ペナルティ
  - クラフト: 技能レベル vs 素材コスト vs 完成品の性能 vs 既存レシピとの差別化
- **基準**: 「入手難易度と製作コストに見合った性能」であるか
  - 単純な±20%比較ではなく、**コスト・パフォーマンス・ユニーク性のトレードオフ**として評価
  - 例: 強力な性能を持つ場合は、素材を希少にするか技能レベルを上げるか、耐久性を下げるなどの代償を設ける
- 必要に応じて数値調整し、Step 7〜8を再実行して確認
```

### 4. `cdda_mod_dev_plan.md`（更新）

「5. 作業フロー > 新規mod作成」を以下に書き換え：

```markdown
### 新規mod作成

```

  └── templates/spec_template.md を使用
  └── mods/<size>/<mod_name>/spec.md

Step 4: CDDAデータとの整合性確認
  └── external/cdda/data/json/ でID・フラグ・値を実在確認
Step 5: 計画書レビュー（AI自己レビュー）

Step 6: AIエージェントで実装


## リスクと対策

- **重複記述のリスク**: CORE.md と cdda_mod_dev_plan.md の両方にフローが記載されるため、将来の変更で乖離する可能性がある。
  - **対策**: CORE.md を「全モデル必読の詳細手順・チェックリスト・プロンプト例」、cdda_mod_dev_plan.md を「人間向けフロー概要図・検証レベル定義・旧mod移植フロー」として役割分担する。詳細な手順はCORE.mdのみに記載し、cdda_mod_dev_plan.mdは概要と参照先を示すに留める。

- **ステップ1の「小規模mod」の基準が曖昧**: 省略条件が主観的になり、重要な設計がスキップされる可能性がある。
  - **対策**: CORE.mdに「小規模modの定義」を4つの具体的条件で明記（新規エントリ5個以下、copy-fromのみ、既存システム拡張のみ、明確な派生元あり）。4条件すべて満たす場合のみ省略可能とする。

- **フロー増大による開発速度低下**: 9ステップ化により、小規模modの開発が煩雑になる。
  - **対策**: 小規模modではStep 1・2を省略可能にする。また、Step 2・5のAIレビューは非同期で実行でき、実装全体の時間を大きく増加させない。計画書テンプレートの構造をシンプルにし、過剰な文書化を防ぐ。
