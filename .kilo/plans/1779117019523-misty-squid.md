# 計画: cdda_mod_dev_plan.md の問題点修正

## 背景
前回のレビューで計画書の過剰設計・非現実的な統計的手法・AIエージェント運用の方法論への逸脱など、7つの主要問題が指摘された。本計画はこれらを修正し、実際の進捗（旧mod移植スクリプト群、小規模mod作成）と整合させる。

## ゴール
- `cdda_mod_dev_plan.md` を実用的なドキュメントに再構成する
- 不要な仕様・ファイル定義を削除する
- 実際に作成済みのファイル群と整合させる

## タスク

### Phase 1: 計画書の内容修正（cdda_mod_dev_plan.md）
1. **統計的手法の廃止（簡易閾値は維持）**
   - Wilson信頼区間、A/Bテスト、差分の差分法(DID)、窓関数などの統計用語と仕様をすべて削除
   - フェーズ2の「同一modを30回実装」を「異なる3〜5種類のmodを各モデルで1回ずつ実装し、エラーパターンを比較」に変更
   - 成功率定義を「統計的信頼区間」から「単純な回数カウント」に変更
   - ルール追加/削除の簡易閾値は維持：
     - 追加：同じエラーが3回以上発生した場合 → `common_errors.md` に追記
     - 削除：該当エラーが直近10回の試行で0回、かつルール追加後も改善が見られない場合 → 手動で削除

2. **ルールライフサイクル管理システムの削除**
   - `rule_manager.py` の仕様を計画書から削除
   - `prompt_builder.py` の仕様を計画書から削除
   - ルールの状態遷移（active/deprecating/inactive）、A/Bテスト、振動減衰メカニズム、アーカイブ復元などの記述を削除
   - ルール管理は手動（Markdownの編集）に統一

3. **検証レベルの簡素化**
   - Level1.5 (Schema検証)、Level2.5 (静的解析)、Level3.5 (異常検知) を廃止
   - Level1 (JSON構文) + Level2 (ゲーム起動確認) + Level3 (意図通り動作・手動) の3段階に戻す
   - balance_checker.py の仕様を計画書から完全に削除

4. **モデル選択ロジックの廃止**
   - エージェント別の詳細な役割分担表と難易度推定基準テーブルを削除
   - 「使えるモデルで適宜実行 → エラーが多ければ高性能モデルに投げる」という簡易フローに置き換え

5. **ベンチマーク構造の見直し**
   - `benchmarks/unseen/` の「ルール更新に使用禁止」という物理的分離の論理を削除（AIに学習機能はないため）
   - `benchmarks/random/` の generator.py 仕様を削除
   - `benchmarks/seen/` と `benchmarks/unseen/` はタスクの難易度分類として維持するが、制約を緩和

6. **ディレクトリ構造とファイル定義の整理**
   - `scripts/` 以下のファイル定義を、実際に存在するもののみに整理（validate.sh、既存の移植スクリプト群）
   - `rules/` 以下のファイル定義を瘦身：CORE.md, version_diff.md, common_errors.md, hints_basic.md を維持、hints_nemotron.md, hints_minimax.md, hints_claude.md, hints_gemini.md, hints_advanced.md, json_schema.md の個別定義を統合・削除
   - `logs/` 以下の複雑なログ構造（errors/, agent_reports/, summarized/）を単純化

7. **旧mod移植フローの正式化**
   - 実際に行った作業（個別の変換スクリプト群：convert_item_types.py, add_activity_level.py, remove_invalid_fields.py 等）を「機械的変換はスクリプトで、創造的デザインはAIで」というハイブリッドアプローチとして計画書に反映
   - パッチ形式の旧mod管理（patches/）を正式なワークフローとして明記

8. **計画書の圧縮**
   - 目標：1500行 → 300行程度
   - 構造：
     1. 目的（2行）
     2. ターゲットバージョン（5行）
     3. 開発原則（10行）
     4. ディレクトリ構成（30行）
     5. 作業フロー（設計→実装→validate.sh→ゲーム起動確認）（30行）
     6. 旧mod移植フロー（30行）
     7. ルールファイルの説明（リンクのみ）（10行）
     8. コスト最適化（簡易）（10行）
     9. 更新履歴（10行）

## 制約・注意点
- 実際のmodファイル（mods/ 以下）やルールファイル（rules/ 以下）の内容自体は、計画書の修正に伴う整合性調整が必要な場合のみ最小限の変更を行う
- external/cdda/ は .gitignore 対象のまま維持
- 統計的手法や自動化システムの仕様は、将来的に必要になった場合でも計画書からは完全に削除し、別途文書化する方針とする
